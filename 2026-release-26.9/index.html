Small And Nice Features

Limits on table size and table count

Hard limits for multi-tenant, temporary, and demo services:

CREATE TABLE t (…) ENGINE = MergeTree ORDER BY id SETTINGS max_table_size_rows = 1000000; -- also max_table_size_bytes_compressed, -- max_table_size_bytes_uncompressed INSERT INTO t … -- Table size limit exceeded: the total number of rows in active data parts -- of table default.t is 1200000, which exceeds the 'max_table_size_rows' setting -- value (1000000). (TABLE_SIZE_LIMIT_EXCEEDED) CREATE DATABASE tenant ENGINE = Atomic SETTINGS max_tables = 100; -- Too many tables in database `tenant`. The limit (database setting `max_tables`) -- is set to 100, the current number is 100. (TOO_MANY_TABLES)

— Checked at the start of an INSERT and when parts are committed, including merges.
— Tables, views, and dictionaries count; ALTER DATABASE … MODIFY SETTING adjusts it.

Developer: Alexey Milovidov.

Parallel replicas for Merge tables

A Merge table over several MergeTree tables can now be read
with parallel replicas — and the aggregation above it is distributed too:

CREATE TABLE logs_all ENGINE = Merge(default, '^logs_'); SELECT toYear(d), count() FROM logs_all GROUP BY 1 SETTINGS enable_parallel_replicas = 1, parallel_replicas_plan_based = 1, parallel_replicas_allow_merge_tables = 1; EXPLAIN: … ReadFromParallelReplicas (Aggregating Union: ReadFromMergeTree (logs_2025), ReadFromMergeTree (logs_2026))

— The Merge is expanded into a union of MergeTree reads before the plan
  is distributed, so no Merge-specific code on the replicas.
— Falls back to a single replica for FINAL and non-MergeTree children.

Developer: Igor Nikonov.

Linear regression aggregate functions

The SQL-standard family, all nine of them:

SELECT regr_slope(y, x), regr_intercept(y, x), regr_r2(y, x), regr_count(y, x) FROM VALUES('x Float64, y Float64', (1, 3.1), (2, 4.9), (3, 7.2), (4, 8.8), (5, 11.1)); -- 1.99 │ 1.05 │ 0.9973 │ 5 — y ≈ 2x + 1

— Also regr_avgx, regr_avgy, regr_sxx, regr_syy, regr_sxy.
— The same names as in PostgreSQL, Oracle, and DuckDB — queries port as is.
— Work with GROUP BY, the -If/-State combinators, and window functions,
  like every other aggregate function.

Developer: mosya415.

Bracket syntax for JSON subcolumns

Paths of a JSON column can be addressed like map keys:

SELECT json['user']['name'], json['tags'] FROM events; -- the same as json.user.name and json.tags SELECT json['user.name'], json['first name'] FROM events; -- keys with dots and spaces — without backticks

— The parser translates it to nested arrayElement calls,
  so the result is the same Dynamic subcolumn, with the same type hints:
  json['a']['b'].:Int64.
— Familiar to everyone coming from Map columns or from other databases.

Developer: Pavel Kruglov.

Hypothetical projections

Define a projection without building it — to check what it would do:

CREATE HYPOTHETICAL PROJECTION p_user ON events (SELECT * ORDER BY user_id); SELECT name, sorting_key FROM system.hypothetical_projections; -- p_user │ ['user_id'] EXPLAIN WHATIF SELECT count() FROM events WHERE user_id = 42; -- Baseline: parts: 1, marks: 123, est_bytes: 4.69 MiB -- With p_user (projection, hypothetical): ...

— Session-scoped; validated like ALTER TABLE … ADD PROJECTION, never materialized.
— Joins CREATE HYPOTHETICAL INDEX from earlier releases.
— In 26.9 the definitions are listed by EXPLAIN WHATIF; cost estimates for them are next.

Developer: Yarik Briukhovetskyi.

arrayFlattenedLength

How many elements are there in a nested array — at all levels?

SELECT arrayFlattenedLength([[1, 2], [3], [4, 5, 6]]), length([[1, 2], [3], [4, 5, 6]]); -- 6 │ 3

— The same as length(arrayFlatten(arr)), without materializing the flattened array.
— Matches PostgreSQL's cardinality, which counts elements at every nesting level
  (our cardinality is an alias of length and counts the outer array only).

Developer: David Meng.

system.statements

The documentation of every SQL statement — inside the server:

SELECT syntax FROM system.statements WHERE name = 'CREATE TOKEN'; -- CREATE TOKEN -- [{VALID UNTIL datetime | VALID FOR interval}] -- [GRANTS (privilege ON object [,...])] SELECT count() FROM system.statements; -- 101

— Columns: name, syntax, description (with examples), parent_name, related.
— The same source that renders docs.clickhouse.com — always matching the binary.
— Joins system.functions, system.settings, system.table_engines, system.formats.

Developer: Robert Schulze.

system.session_query_ids

"Which queries did I just run?" — without assigning query ids by hand:

SELECT count() FROM numbers(10); SELECT sum(number) FROM numbers(100); SELECT query, query_duration_ms FROM system.query_log WHERE query_id IN (SELECT query_id FROM system.session_query_ids) AND type = 'QueryFinish' ORDER BY event_time_microseconds; -- SELECT count() FROM numbers(10) │ 234 -- SELECT sum(number) FROM numbers(100) │ 112

— Query ids of the current session, in execution order (sequence_number).
— For testing and benchmarking scripts; session_query_ids_history_size (1000)
  bounds it, TRUNCATE TABLE system.session_query_ids clears it.

Developer: Vladimir Cherkasov.

S3Queue without Keeper coordination

A third mode for the S3Queue engine, for a single ingesting server:

CREATE TABLE queue (WatchID UInt64, URL String, EventDate Date) ENGINE = S3Queue('s3://bucket/landing/*.parquet', NOSIGN, 'Parquet') SETTINGS mode = 'exclusive'; CREATE MATERIALIZED VIEW mv TO events AS SELECT * FROM queue;

— unordered and ordered track every file in Keeper, so that many servers
  can share one queue. exclusive tracks files in the memory of the server:
  no Keeper round trip per file — for high-throughput ingestion from
  a bucket that belongs to this server alone (e.g. a local MinIO).
— Battle-tested: the contributor ran it in production for years before upstreaming.

Developer: Ivan Tkatchev.

Performance Improvements

min, max, count from column statistics

Column statistics (on by default since 26.4) store the exact min and max
of every numeric-like column per part. Now aggregations read them:

SELECT min(EventDate), max(EventDate), count() FROM hits; -- ClickBench Q6, 100M rows: no data is read at all EXPLAIN … Aggregating └── ReadFromPreparedSource (_statistics_min_max_projection)

Example: 26.8: 8–24 ms   26.9: 2 ms — a full column scan becomes a metadata lookup.

— Parts without statistics are read normally and merged in;
  disabled under FINAL, sampling, lightweight deletes. Setting: use_statistics_for_min_max_aggregation.

Developer: Alexey Milovidov.

skip_empty_columns_on_insert

Wide tables where most columns are empty in most inserts
(per-tenant or per-partition schemas, sparse JSON) — stop writing the emptiness:

CREATE TABLE wide (id UInt64, a String, b UInt64, c Array(UInt32), j1 JSON, j2 JSON) ENGINE = MergeTree ORDER BY id SETTINGS skip_empty_columns_on_insert = 1, serialization_info_version = 'with_missing_columns'; INSERT INTO wide (id, a, j1) … -- b, c, j2 are all defaults in this block -- serialization.json: "missing_columns": [{"name":"b","type":"UInt64"}, {"name":"c",...}, {"name":"j2",...}] -- files in the part: 49 → 33; no data streams at all for b, c, j2

— Reads reconstruct the default of the recorded type; the marker survives merges,
  mutations, renames, replication, backups.
— Opt-in: older servers cannot read such parts — keep the old
  serialization_info_version during a rolling upgrade.

Developer: Amos Bird.

One round trip less in the native protocol

At the end of every query the server sends a burst of tiny messages:
profile info, progress, profile events, an empty block, end of stream …
Each used to be its own TCP packet:

$ tcpdump -i lo 'tcp src port 9000' # SELECT 1, server → client, after the handshake 26.8: 23 10 10 3133 14 10 1 — 7 packets 26.9: 23 3278 — 2 packets

— After an idle period Linux shrinks the congestion window to initcwnd;
  a burst longer than that waits for an ACK — a full extra round trip.
  On a 30 ms link that was ~2x latency for clients that idle between queries.
— The end-of-query messages are now batched into one socket write.

Developer: Kaviraj Kanagaraj.

LIKE and ILIKE with text indexes

The text index answered %word% patterns since 26.7 by scanning its dictionary.
Now prefix and suffix patterns work too:

SELECT count() FROM docs WHERE body LIKE 'clickhouse%'; -- startsWith SELECT count() FROM docs WHERE body LIKE '%clickhouse'; -- endsWith EXPLAIN indexes = 1: Prewhere: endsWith(body, 'clickhouse') AND __text_index_idx_endsWith_… Skip: Name: idx, Granules: 4/2442

— The index works as a hint: the matching tokens' posting lists select the granules,
  the original condition re-checks the rows.
— LIKE … ESCAPE patterns can use text, ngram, token, and sparse-gram indexes now.
— An index with the array tokenizer serves arbitrary LIKE/ILIKE patterns.

Developers: Elmi Ahmadov, Groene AI.

Faster on AArch64

Graviton, Ampere, Apple, NVIDIA Grace — a batch of ARM-specific fixes:

— memcpy: the small-copy helper used in string, join, and part-reading paths
  compiled into a libc memcpy call on AArch64 — the exact call it exists to avoid
  (fixed on x86 in 2024, the NEON branch was never updated). Now inline: 1.35x at 4–16 bytes.
— Filters: countBytesInFilter fell back to a scalar loop (~8 GB/s);
  direct NEON register accumulation — up to 15x faster counting of filter bytes.
— Also: numbers and index fills, T64 codec, roundDuration/roundAge,
  UTF-8 validation, 128-bit division — all vectorized or branchless now.

Example: DISTINCT over 100M short strings, one thread, Graviton3:

26.8: 12.4 sec.   26.9: 7.6 sec. (1.6x)

Developers: Groene AI, Joshua Dorst, Harikrishnan Prabakaran.

Faster k-way merges

Merging sorted streams is the core of MergeTree: background merges, FINAL,
ORDER BY, optimize_on_insert. Three optimizations, motivated by
Maksim Kita's analysis of k-way merge:

— Multi-column and collated sorting keys: a sorted array of cursors
  instead of a heap — 7–8% faster.
— Non-intersecting parts (the common case after time-ordered inserts):
  the whole cursor is detected as one batch in O(1) comparisons.
— Runs of duplicate keys inside a part are skipped:
  SELECT … FINAL from ReplacingMergeTree uses up to 40% less CPU,
  insert-time deduplication with optimize_on_insert is ~3x faster with many duplicates.

Developer: Alexey Milovidov.

Index usage after ARRAY JOIN

A condition on an ARRAY JOIN element now drives skip-index analysis,
the same way arrayJoin(col) IN (…) already did:

CREATE TABLE t (id UInt64, tags Array(String), INDEX bf tags TYPE bloom_filter) … SELECT count() FROM t ARRAY JOIN tags AS tag WHERE tag IN ('rare7', 'rare8'); -- 26.8: Granules 1223/1223 — full scan -- 26.9: Skip bf — Granules 2/1223

— The arrayJoin function is now planned as the ARRAY JOIN operator internally,
  so both spellings share the optimizations.
— A WHERE on the element is applied before the expansion: elements that
  do not match are never turned into rows, and other columns are not replicated for them.
— Bloom filters on Array columns also serve arrayJoin(col) = const and GLOBAL IN.

Developers: Yarik Briukhovetskyi, Groene AI.

Faster reading of subcolumns from object storage

A JSON column is hundreds of substreams; on S3 every substream's marks
were loaded one after another — one round trip each, in the reading thread:

-- the public datasets collection, attached from Cloudflare R2 as a plain_rewritable disk: ATTACH DATABASE datasets UUID 'e053c139-f7b8-4c82-acb7-6b259c5b19e8' ENGINE = Atomic SETTINGS disk = disk(type = 's3_plain_rewritable', endpoint = 'https://data.clickhouse.com/public-datasets/db/', no_sign_request = true, readonly = true), lazy_load_tables = true; SELECT data.wiki.:String AS wiki, count() AS edits FROM datasets.wikipedia_edits WHERE time >= now() - INTERVAL 1 DAY AND data.type.:String = 'edit' GROUP BY wiki ORDER BY edits DESC LIMIT 5; -- data is a JSON column, ~1M events/day

— Marks of all streams are loaded asynchronously and in parallel by default now
  (load_marks_asynchronously); marks of empty streams are not loaded at all;
  JSON metadata streams are no longer read twice; reads in packed parts are bounded to the file.
— In the PR's test (1104 substreams, 30 ms per request): 64 sec → 2.5 sec.

Developers: Alexey Milovidov; Rory Shanks (subcolumns in wide parts); Pavel Kruglov (JSON shared data blocks).

Better reuse of connections to object storage

A read up to the end of an object was an open-ended Range: bytes=N- request.
The connection was returned to the pool only after EOF — which the MergeTree reader,
sized to exactly the remaining bytes, never observed. So it stayed occupied until
the end of the query, and every new stream opened a new TLS connection:

-- one row of a JSON column with ~500 substreams per part (from the PR): 26.8: 2333 connections for 5372 requests -- "Too many active sessions in group Disk, count 1900" -- wikipedia_edits, the query from the previous slide: DiskConnectionsCreated: 26.8: 235 26.9: 59

— The request is now Range: bytes=N-M; the connection is released as soon as
  the range is read and reused by the next stream.
— Fewer TLS handshakes, no session-limit warnings, less latency per stream.

Developer: Alexey Milovidov.

Conflict detectors in join reordering

Which join orders are valid when SEMI, ANTI, and OUTER joins are involved?
The optimizer treated every non-inner join as a barrier: inner-join islands
were reordered independently, a selective SEMI join stayed pinned on top.

SET query_plan_optimize_join_order_algorithm = 'dpsub', query_plan_optimize_join_order_use_conflict_detector_c = 1; EXPLAIN SELECT count() FROM big1 JOIN big2 ON big1.k = big2.k LEFT SEMI JOIN small ON big1.k = small.k; -- before: (big1 ⋈ big2) ⋉ small -- 10M ⋈ 10M first, then filter -- after: big2 ⋈ (big1 ⋉ small) -- the 1000-row semi join goes first

— CD-A and CD-C from the SIGMOD'13 paper "On the Correct and Complete Enumeration
  of the Core Search Space" (Moerkotte, Fender, Eich) — the state of the art.
— For 7 relations CD-C explores ~12x more valid plans than before.
— Available with the dpsub algorithm; opt-in in 26.9.

Developer: Fisnik Kastrati.

Faster recursive CTEs

Each step of a recursive CTE writes its result into an intermediate Memory table,
which the next step reads — one block per produced chunk:

WITH RECURSIVE frontier AS ( SELECT 1 AS node, 0 AS depth UNION ALL SELECT e.dst, depth + 1 FROM edges e JOIN frontier f ON e.src = f.node WHERE depth < 6) SELECT count() FROM frontier;

— Graph searches whose frontier is built from many granule-sized reads
  (or ARRAY JOIN expansions) accumulated thousands of tiny blocks per step,
  and every following step paid the per-block overhead to scan the working table.
— Chunks are now squashed before the write, with the same thresholds
  as a regular INSERT into a Memory table. No new settings.

Developer: Zach Naimon.

Faster uniq and uniqCombined

Approximate distinct counting per group — the shape of every
"unique users per page" query:

SELECT URL, uniq(UserID) FROM hits GROUP BY URL; SELECT k, uniqCombined64(v) FROM t GROUP BY k;

— With many interleaved groups every row jumps to a different aggregation state,
  and the hash set inside each state is a cache miss.
— The hashes of a batch are now computed first and the destination cells are
  prefetched — the same trick the aggregator uses for its own hash table.
— Single-argument uniq, uniqCombined, uniqCombined64 on scalar types.

Also in 26.9: uniqExact of aggregate states, JSON, and Variant hashes
without a per-row buffer copy — 33% faster for 200-byte states.

Developers: Manuel, Groene AI.

JOIN: row-major hash table payload

The right side of a hash join is stored column by column. Building the output
then gathers one value per column per matched row — a scattered loop.

before: col1 Int32 │ col2 String │ col3 UInt8 │ col4 Float64 — row N: col1[N], col2[N], col3[N], col4[N] after: ROW STORE (col1 + col3 + col4, contiguous per row) col2 String (still columnar) ┌──────┬──────┬────────┐ ┌──────────┐ │ col1 │ col3 │ col4 │ ← row N: one pointer, one copy │ .... │ └──────┴──────┴────────┘ └──────────┘

— Fixed-size columns under a size threshold are packed into a row store;
  output construction becomes a tight loop per column.
— On by default: enable_hash_join_row_store, min_rows_ratio_for_hash_join_row_store.
— Also: LEFT SEMI / LEFT ANTI joins that select no right column build a
  keys-only hash table and release the right blocks — up to 1.5x faster, half the memory.

Developers: Hechem Selmi (row store), Nikita Taranov (keys-only tables).

GROUP BY: three small things

— GROUP BY without aggregate functions (a set of keys) started prefetching
  only at a much higher cardinality than GROUP BY with aggregates. Now both start
  at the same point — where the hash table stops fitting in the L2 cache.
  Plus inlining of a few hot functions on that path.

— The adaptive aggregator (26.8) falls back to the ordinary algorithm when rare keys
  or aggregate arguments are too wide to copy profitably — heavy string columns
  run at the ordinary speed and memory; adaptive_aggregator_freeze_threshold_bytes.
  The old sharding aggregator is removed in its favor.

— The bucket top-K optimization (keep each two-level bucket's best n groups
  when a final aggregation feeds ORDER BY … LIMIT n) got its own setting,
  query_plan_aggregation_bucket_top_k, is visible in EXPLAIN, and no longer
  materializes every group's key for a statistic only parallel replicas consume.

Developers: Nikita Taranov, Nihal Z. Miaji.

Text indexes: faster everything

— Merges of text indexes: no bitmap allocation when deserializing embedded
  and small posting lists, no roaring conversion when building the output list.

— Lazy posting lists: hasToken, hasAnyTokens, hasAllTokens intersect and unite
  posting lists at packed-block granularity instead of materializing bitmaps.

— Phrase search: positions are stored in packed blocks; only the blocks
  that cover candidate rows are read.

— The splitByNonAlpha and splitByString tokenizers are faster; UTF-8 validation
  in text index conditions is vectorized on x86 and ARM.

— Fixed: a text index filter combined with ORDER BY … LIMIT stopped using the index
  and read the whole column.

— New: the keyValuePairs tokenizer indexes a Map(String, String) column and answers
  map['key'] = 'value' from the index; splitByRegexp(re, 1) extracts tokens by capture group.

Developers: Anton Popov, Elmi Ahmadov, Jimmy Aguilar Mena.

Main Features

LIMIT with boundary conditions

Select rows by where they are in the stream, not by position:

SELECT number FROM numbers(10) ORDER BY number LIMIT 3 AFTER number >= 5; -- 5, 6, 7 SELECT number FROM numbers(10) LIMIT UNTIL number >= 3; -- 0, 1, 2 SELECT number FROM numbers(10) LIMIT AFTER number >= 2 UNTIL number >= 6; -- 2, 3, 4, 5 SELECT number FROM numbers(10) LIMIT 2 AFTER number IN (2, 6) ALL; -- 2, 3, 6, 7

— "The rows from the first error until the next checkpoint", "N rows after every marker" —
  in one pass over an ordered stream, instead of window functions or client-side cutting.
— AFTER is inclusive, UNTIL exclusive; the conditions may use columns that are not selected.

Developer: Zakhar Kravchuk.

GRANTS per authentication method

One user, several credentials — each with its own limit on what it can do:

ALTER USER app ADD IDENTIFIED WITH sha256_password BY 'readonly_key' VALID FOR INTERVAL 30 DAY GRANTS (SELECT ON default.sales); -- a session authenticated with readonly_key: SELECT count() FROM default.sales; -- 1000 INSERT INTO default.sales VALUES (1, 'x', 1); -- ACCESS_DENIED: Not enough privileges

— The rights of the session are the intersection of the user's grants
  with the listed ones. The clause never adds rights.
— Tied to the user: shown as the user in query_log and processes,
  stops working when the user is deleted, narrows when the user loses grants.
— Visible in SHOW CREATE USER and system.users.auth_grants.

Developer: Alexey Milovidov.

CREATE TOKEN

Tokens for applications — generated by the server, for the current user:

GRANT CREATE TOKEN ON *.* TO app; -- as app: CREATE TOKEN VALID FOR INTERVAL 7 DAY GRANTS (SELECT ON default.sales); ┌─token────────────────────────────┬─────────valid_until─┐ │ sbnvAg6tBx306T8mrhtLaCxwhiEKTktq │ 2026-09-24 00:25:21 │ └──────────────────────────────────┴─────────────────────┘ $ clickhouse client --user app --password sbnvAg6tBx306T8mrhtLaCxwhiEKTktq

— Sugar for ALTER USER <me> ADD IDENTIFIED WITH sha256_password BY '<random>'
  with the same VALID FOR / GRANTS clauses: 32 random characters, stored hashed, shown once.
— Without a lifetime, a token lives create_token_default_ttl_seconds (30 minutes).
— Works wherever a password works: HTTP, native, MySQL, PostgreSQL protocols.

Developer: Alexey Milovidov.

REFRESH … APPEND INCREMENTAL

Refreshable materialized views can now process only the new rows
committed to the source since the previous refresh:

CREATE TABLE src (ts DateTime, k UInt32, v UInt64) ENGINE = MergeTree ORDER BY ts SETTINGS enable_block_number_column = 1, enable_block_offset_column = 1; CREATE MATERIALIZED VIEW hourly REFRESH EVERY 1 HOUR APPEND INCREMENTAL ENGINE = MergeTree ORDER BY k AS SELECT k, sum(v) AS s, count() AS c FROM src GROUP BY k; -- system.view_refreshes.read_rows after 1000 + 10 inserted rows: 1010 — not 2010

— The refresh cursor is the source's block numbers, hence the two table settings.
— Between the classic MV (per-insert) and a full refresh (re-read everything):
  batch aggregation of the delta, on a schedule.
— Into an Iceberg target it is exactly-once: the cursor is committed in the snapshot summary.

Developer: Smita Kulkarni.

Experimental Features

Kusto Query Language, reimplemented 🧪

The KQL dialect was contributed in 2022 and abandoned: it translated a token stream
into SQL text and reparsed it — 298 format sites, no AST, an injection hole in
string operators, 28 functions registered that did nothing.

SET dialect = 'kusto', allow_experimental_kusto_dialect = 1; print q = 7 / 2, sub = substring('abcdefg', -3, 2), c = '50x' contains '50%' -- before: 3.5 │ 'ab' │ true (the needle was pasted into a LIKE pattern) -- now: 3 │ 'ef' │ false — what Kusto returns

— Now a dedicated lexer, parser, and AST translation: needles are literals,
  nothing is representable as an injection.
— The supported subset is smaller and documented; anything outside it
  is rejected by name instead of being mistranslated.

Developer: Alexey Milovidov.

Trino SQL dialect 🧪

Queries written for Trino (and Presto, Athena) run as they are:

SET dialect = 'trino', enable_trino_dialect = 1; SELECT x, TRY_CAST('abc' AS INTEGER) AS c, cardinality(ARRAY[1, 2, 3]) AS n FROM UNNEST(ARRAY[10, 20, 30]) AS t(x) OFFSET 1 LIMIT 5; -- 20 │ NULL │ 3 -- 30 │ NULL │ 3 SELECT transform(ARRAY[1, 2, 3], x -> x * 2), approx_percentile(v, 0.9), date_trunc('month', TIMESTAMP '2026-09-17 10:00:00'), ROW(1, 'a') FROM (VALUES (1), (2), (3), (10)) AS t(v); -- [2,4,6] │ 10 │ 2026-09-01 │ (1,'a')

— Not a separate grammar: a token-level syntax translation, the standard parser,
  and an AST-level mapping of ~340 Trino functions (renames, argument order, lambdas last).
— Migrate dashboards and pipelines first, rewrite queries later.

Developers: Alexey Milovidov, Ethan Lin.

Data Lakes

Create a new Delta Lake table

Reading Delta Lake tables since 23.x, writing since 26.2 — now ClickHouse
can create them, from scratch:

SET allow_delta_lake_writes = 1, allow_delta_lake_create_table = 1; CREATE TABLE trips (id Int64, name String, score Float64) ENGINE = DeltaLake('s3://bucket/warehouse/trips/', '<key>', '<secret>'); INSERT INTO trips VALUES (1, 'a', 1.5), (2, 'b', 2.5); SELECT * FROM trips ORDER BY id; -- _delta_log/00000000000000000000.json: {"commitInfo":{"operation":"CREATE TABLE","engineInfo":"ClickHouse", ...}} -- _delta_log/00000000000000000001.json: the INSERT; one Parquet data file

— The initial commit is written through delta-kernel-rs; also attaches to an existing
  _delta_log, or registers a table into a Unity catalog. S3, Azure, and local storage.
— Writes now cast with an accurate cast: 300 into a Delta byte throws instead of truncating.
— Not yet: PARTITION BY for new tables.

Developer: Smita Kulkarni.

Parallel decoding of Iceberg manifests

Planning a query over an Iceberg table means walking its manifests: fetch, parse Avro,
then prune every entry by partition and min/max. That walk ran serially:

— 26.8 prefetched the next manifest — overlapping only the fetch, not the decode.
— 26.9 decodes manifests concurrently, streaming surviving entries into a bounded
  queue as they are produced — no batch is ever materialized, backpressure applies
  within a manifest, peak memory is the in-flight manifests plus the queue.

Example (from the PR): a production table, 18 data manifests, 113 MB, ~75K entries:

serial: 8.45 sec.   4 threads: 2.55 sec.   16 threads: 1.68 sec.

— iceberg_manifest_decode_concurrency (default 4) bounds it, for delete and data
  manifests alike; the old iceberg_delete_manifest_decode_concurrency is an alias.

Developer: Aaron Harlap.

Pruning by the Iceberg manifest list

The manifest list carries per-manifest partition summaries: lower_bound, upper_bound,
contains_null. Now they prune whole manifests before any of them is opened:

CREATE TABLE ice (id Int64, m UInt32, d Date, v Float64) ENGINE = Iceberg(…) PARTITION BY m; -- 8 inserts, one month each SELECT count() FROM ice WHERE m = 5; -- metadata files read: 41 → 7 (use_iceberg_manifest_list_partition_pruning) -- data files listed: 39 → 5 (use_iceberg_partition_pruning, per entry, as before)

— Three levels now: manifest list → manifest entries → Parquet row groups.
— The fewer manifests decoded, the less there is to parallelize (previous slide).
— ClickHouse also writes the partition field summaries into the manifest list since 26.9.

Developer: Konstantin Vedernikov.
